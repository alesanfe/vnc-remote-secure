# Maturity Model — Self-Assessment

Self-assessment against the CNCF-style maturity ladder (A–E) and the
0–4 professionalism matrix. Evidence links make each score checkable
rather than aspirational.

## Levels A–E

| Level | Claim | Evidence |
|-------|-------|----------|
| **A — Functional** | ✅ Met | Runs on Linux+Windows; documented install (`docs/installation/`); versioned releases; 1758+ tests; no published secrets (gitleaks CI) |
| **B — Maintainable** | ✅ Met | Three-layer architecture + import-linter contracts; dep policy in `pyproject.toml` + Dependabot; full CI matrix; ADRs make decisions transferable; `CONTRIBUTING.md` + `docs/developer/` |
| **C — Production-ready** | ✅ Met | Reproducible deploy (single CLI, `doctor`, `verify`); metrics/logs/alerts/runbooks (`docs/runbook/`); backup+restore tested (`tests/unit/core/test_backup.py`, recovery runbook); security in SDLC (bandit/semgrep/CodeQL/Trivy/fuzz); capacity documented (`slo.md`) |
| **D — High confidence** | ✅ Mostly | SBOM + SLSA attestation + SHA-256 per release; threat model + risk register + incident response; audit chain verifiable (`/audit/verify`). **Residual**: no funded external audit, no formal disaster drill cadence yet (see `runbook/drills.md`) |
| **E — Continuous improvement** | ◐ Partial | Consistency-audit reports in `docs/reports/`; complexity audits + refactors done as campaigns. **Missing**: DORA metrics collection, periodic audit calendar, product-level usage metrics (out of scope — self-hosted tool) |

## 0–4 Dimension matrix

| Dimension | Score | Justification |
|-----------|-------|---------------|
| Requirements | **3** | `REQUIREMENTS.md`: FRs with acceptance criteria traced to tests; measured NFRs |
| Architecture | **3–4** | Documented + *verified*: import-linter contracts, adapter-contract tests, parity matrix regenerated by `tools/parity_matrix.py` |
| Tests | **3** | Pyramid (unit/integration/e2e/security/soak), risk-based; not yet adaptive (no coverage gate per change) |
| Security | **4** | SSDF lifecycle embedded: threat model, SAST/DAST deps, fuzz, secrets scanning, fail-closed policies, disclosure process (RFC 9116) |
| Deployment | **3** | Automated install/upgrade/rollback; progressive deployment N/A for self-hosted single-node |
| Operations | **3** | Logs+metrics+alerts+SLI/SLO+error budgets; not yet "continuous improvement" loop |
| Recovery | **3** | Backup+restore+rollback verified by tests; disaster *drills* defined but not yet scheduled (`runbook/drills.md`) |
| Documentation | **4** | Versioned, structured by purpose (Diátaxis-ish), kept honest by contract tests + consistency audits |
| Data | **2** | Data model + retention doc exists; data governance is minimal — appropriate for a local-first tool with no PII pipeline |
| Team | **1–2** | Single maintainer (accepted risk R-14); CODEOWNERS + governance mitigate |

**Total ≈ 30–31 / 40** — professional, maintainable, production-ready.
The scores that matter most for *this* product (security, ops,
recovery) sit at the top; the weak spots are team-scale concerns
that a single-maintainer project cannot fully resolve.

## Proportionality note

Per the CNCF model: not every project needs level E. For a self-hosted
security tool the *binding* dimensions are security/reliability/
recoverability — those carry the investment. Team-scale and
product-analytics dimensions stay deliberately light.
